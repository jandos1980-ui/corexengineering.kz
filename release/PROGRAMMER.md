# Инструкция программисту — CoreX Engineering

Разместите готовый сайт на **https://corexengineering.kz/** в корне домена, настройте PHP и почту, затем проведите серверную приёмку. Комплект содержит 24 страницы RU/EN/KK. Для статической части не нужны Node.js, Python, база данных или сборка на сервере. Подробные примеры Nginx/Apache и настройка обработчика — в [INSTALL.md](INSTALL.md).

## 1. Комплект и размещение

Скачайте **corex-site.zip из Assets актуального клиентского релиза**:

https://github.com/jandos1980-ui/corexengineering.kz/releases/latest/download/corex-site.zip

`Code → Download ZIP` и автоматический `Source code (zip)` содержат исходники предпросмотра GitHub Pages с `noindex`. Для основного домена нужен клиентский архив: сборщик создаёт production canonical/hreflang, robots.txt и sitemap.xml.

Сравните SHA256 архива с опубликованным `corex-site.zip.sha256`, проверьте файлы по `SHA256SUMS.txt`. Сохраните архив и `VERSION.txt` с исходным коммитом для отката.

Загрузите **содержимое `site/` в web root**: `index.html` должен лежать непосредственно в корне сайта. Сохраните вложенность и регистр имён файлов. INSTALL.md, PROGRAMMER.md, VERSION.txt и SHA256SUMS.txt оставьте вне публичного каталога. В исходниках инструкции лежат в `release/`, в клиентском архиве — на верхнем уровне.

| Путь | Содержимое |
| --- | --- |
| `/`, `/solutions/` | Главная и 7 направлений RU |
| `/en/`, `/en/solutions/` | Главная и 7 направлений EN |
| `/kk/`, `/kk/solutions/` | Главная и 7 направлений KK |
| `assets/`, `documents/`, `components/`, корневые CSS/JS | Медиа, шрифты, PDF, оформление и интерактивность |
| `api/contact.php` | Единый обработчик заявок |
| `404.html`, `robots.txt`, `sitemap.xml` | Ошибка 404 и индексация |

## 2. Хостинг, домен и форма

1. Сохраните текущий сайт, настройки хостинга/Tilda и DNS, подготовьте возврат. До смены DNS проверьте новый сервер через hosts или закрытый тестовый хост. Production-архив разрешает индексацию: закройте тестовый хост авторизацией либо `X-Robots-Tag: noindex`; на основном домене уберите этот заголовок.
2. Подключите PHP **8.1+** к `api/contact.php`. Статический Nginx из INSTALL.md требует дополнения PHP-FPM по инструкции хостинга. PHP должен исполняться, а не отдаваться исходным текстом. Настройте MIME-типы CSS/JS/SVG/WebP/WOFF2/PDF и сжатие текстовых ресурсов.
3. Настройте TLS для основного имени и www; перенаправления HTTP → HTTPS и www → без www должны сохранять путь и параметры, не создавать циклов.
4. Меняйте только необходимые веб-записи DNS, проверьте A и AAAA. Сохраните MX и почтовые TXT. Для отправителя `website@corexengineering.kz` настройте разрешённый транспорт хостинга, SPF/DKIM и проверьте DMARC.

Форма делает JSON POST на `api/contact.php` того же домена. В коде фиксированы получатель **info@corexengineering.kz** и отправитель **CoreX Engineering <website@corexengineering.kz>**; `Reply-To` содержит проверенный email посетителя. Переменной окружения для получателя нет. Используется PHP `mail()`. Если провайдер требует SMTP-библиотеку, замените вызов на его серверный транспорт; секреты храните вне Git и web root.

Создайте приватный каталог вне web root, доступный на запись PHP-пользователю, и задайте переменные в окружении **самого PHP-FPM/handler**:

| Переменная | Значение |
| --- | --- |
| `COREX_CONTACT_RATE_DIR` | Абсолютный путь к приватному каталогу, например `/var/lib/corex-contact` (Linux: подходящий владелец, права 0700) |
| `COREX_CONTACT_RATE_SALT` | Случайная секретная строка не короче 32 символов; пример генерации: `openssl rand -hex 32` |
| `COREX_CONTACT_ENABLED` | `1` после настройки транспорта и каталога; по умолчанию POST возвращает 503 |

Экспорт в интерактивной shell не гарантирует доступность переменных PHP-FPM. Проверьте настройки пула/хостинга и перезагрузите сервис. GitHub Pages и статический сервер PHP не исполняют: отправка там не работает.

Сохраните ограничения API: JSON до 16 КБ; Origin только `https://corexengineering.kz` или `https://www.corexengineering.kz`; обязательные имя/компания/email/задача; пустой honeypot `website`; язык `ru`/`en`/`kk`. Для закрытого тестового домена временно добавьте точный Origin в `$origins`, затем удалите. Origin и honeypot — базовые меры против ботов.

Лимит — 5 попыток за час на IP и интервал не менее минуты; общая сеть посетителей делит лимит. В приватном `contact-rate.json` находятся хеши IP и время; содержимое заявок на диск не записывается. За прокси настройте доверенные адреса на сервере, не доверяйте произвольному `X-Forwarded-For`. Включите `display_errors=Off`, логи без текста заявок, ограничение POST до 16 КБ на сервере. Не кэшируйте API и не перенаправляйте его на главную.

## 3. Серверная приёмка

1. **Сайт:** все 24 страницы → 200; меню, языки, FAQ, оборудование, сертификаты, PDF, email и телефон работают. На 320–390 px и desktop нет горизонтальной прокрутки, изображения и шрифты загружаются.
2. **Футер:** без взаимодействия цветные ячейки не появляются. Мышь, касание и движение пальца дают подсветку с затуханием 2 с; повторное касание работает. Возврат к футеру или вкладке не запускает подсветку. При reduced-motion цветная анимация отключена. Проверьте нативную прокрутку пальцем.
3. **Без JS и при отказе app.js:** форма скрыта, доступна ссылка `mailto:info@corexengineering.kz`, данные не отправляются через URL. Не удаляйте исходные `hidden/disabled` без замены механизма: нативная HTML-отправка не соответствует JSON API.
4. **PHP:** выполните `php -l api/contact.php`. GET → 405; POST при выключенном обработчике → 503. После включения и с допустимым Origin/JSON: неверный email или пустая задача → 422, чужой Origin → 403, неверный Content-Type → 415, слишком большое тело → 413 (либо заданный отказ сервера), частые запросы → 429. Ранний отказ по настройке/Origin может маскировать следующий тест.
5. **Реальная почта:** отправьте заявки с главной и внутренней страницы каждого языка, проверьте все поля, кириллицу/казахские символы, получение на info@corexengineering.kz и ответ через Reply-To. Выдерживайте интервал лимитера. Ответ `200`, `{"ok":true,"code":"accepted"}` подтверждает принятие транспортом, не доставку во входящие.
6. **Ошибки:** при ошибке сети/сервера поля сохраняются, успех не показывается, повторное нажатие во время запроса заблокировано. Тайм-аут клиента — 20 с; письмо могло уйти, поэтому перед повтором проверьте ящик. Поля сохраняются и после успеха.
7. **SEO/сервер:** robots.txt и sitemap.xml → 200; неизвестный и глубокий путь (например `/kk/несуществующая/страница/`) → оформленная страница с HTTP 404. Не включайте SPA fallback на главную с кодом 200. На 24 основных страницах и в HTTP-заголовках нет noindex; у 404 он сохранён. После смены DNS повторите проверки с внешней сети, включая TLS/редиректы и почту домена.

В production canonical каждой страницы указывает на её HTTPS URL; hreflang содержит `ru-KZ`, `kk-KZ`, `en`, `x-default` (RU), sitemap — 24 адреса. Для другого домена или подпапки обновите SEO-адреса и повторно проверьте ссылки. После запуска передайте sitemap в подтверждённые Google Search Console и Яндекс Вебмастер.

Ранее проверены Chromium (24 страницы × 4 ширины), no-JS, валидация и имитированные ответы API, отдельно mouse/touch-футер. **Исполнение PHP, реальная доставка, DNS, TLS и конфигурация клиента локально не проверены.** Safari, Firefox и физические устройства в основной прогон не входили. Серверную приёмку завершает принимающий программист. Подробности в исходниках: `release/VALIDATION-2026-10-20.md`.

## 4. Правки, выпуск и откат

Тексты находятся в HTML трёх языков; общие CSS/JS влияют на все страницы. Футер реализован в `components/ui/background-boxes.js` и `.css`: автозапуска нет, сенсорные обработчики passive, вне экрана/в скрытой вкладке подсветка очищается. Текущая версия JS — `touch-only-20261020`.

После изменения CSS/JS обновите `?v=...` во всех подключающих HTML; при CDN очистите кэш или проверьте, что query-параметры входят в его ключ. HTML должен своевременно перепроверяться браузером. При смене контактов проверьте тексты, ссылки, `app.js`, PHP и документацию. При добавлении страниц обновите языковые ссылки, SEO и сборщик/проверку: количество страниц сейчас проверяется как 24.

Вносите правки в исходный репозиторий, затем собирайте и размещайте архив целиком. Из корня исходников (Python 3.9+ только на машине разработчика):

```bash
python release/build_release.py --output ../corex-site.zip
python release/verify_release.py ../corex-site.zip
```

Сборщик формирует production SEO и контрольные суммы; проверка проверяет состав, ссылки, ресурсы и SEO архива. Это не проверка PHP/почты/хостинга. Правки только в распакованной копии будут потеряны при следующем выпуске.

Храните предыдущие файлы и конфигурацию отдельно; переключайте комплект целиком, не смешивая выпуски. При проблеме с почтой уберите `COREX_CONTACT_ENABLED=1` (форма получит 503), проверьте доступность почтовых контактов. При неудачном запуске восстановите предыдущий комплект/конфигурацию или согласованные веб-записи DNS. Секреты и каталог лимитов остаются вне web root.

Передайте владельцу версию и SHA256 архива, дату запуска, результат реального тестового письма, изменённые DNS-записи, место резервной копии и способ отката. Доступы передавайте отдельным защищённым каналом, не через документ или Git.
